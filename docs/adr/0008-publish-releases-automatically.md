# Publish Releases Automatically

Bakalah release automation should publish a GitHub Release from the merged Release Branch workflow after it validates the exact merged revision, builds and signs every release APK, creates `SHA256SUMS`, and verifies the complete artifact set. The workflow creates the annotated release tag only after local verification, uses a draft GitHub Release as repairable staging, verifies the remote tag, reviewed notes, asset names, upload states, sizes, and digests, then automatically makes the Release public. This supersedes the manual draft checkpoint from [ADR 0001](./0001-create-releases-as-drafts.md); temporary draft staging does not require maintainer approval.

Release intent remains a reviewed `release/MAJOR.MINOR.PATCH` pull request merged into `main`, as described in [ADR 0002](./0002-auto-tag-merged-release-branches.md). Ordinary reruns may resume a partial draft only when the annotated tag still targets the intended merge commit; matching assets are retained, mismatched expected assets are replaced, and unexpected assets fail closed. A narrow manual recovery workflow may rebuild from that existing immutable tag but cannot create or move tags, invent release intent, or mutate a public Release. Once published, the tag, notes, checksum manifest, and APKs are immutable; corrections require a new Release Version.

The former GitHub App workflow is disabled atomically with this cutover. Its installation and secrets may remain temporarily unused until the first release through the new path succeeds, after which they should be removed.
